## What

**The scheme** — `oauth_authorization_code` in `@graft/proxy`, injecting `Authorization: Bearer <accessToken>`. The person enters `clientSecret` (`SCHEME_CREDENTIAL_FIELDS`); the consent's `accessToken`, `refreshToken` and `expiresAt` are written by Graft into the **same encrypted record** — a new import-free table, `SCHEME_ISSUED_CREDENTIAL_FIELDS`, so the form never renders them and the entry rule refuses them. Non-secret `schemeConfig`: `authorizeUrl`, `tokenUrl` (required), `scopes`, `clientAuth` (optional, default `body` — what Google, GitHub and Microsoft document), and `clientId` in a new `personEntered` bucket of `SCHEME_PARAMETERS`: required at registration, absent from the agent's proposal, rendered by the form as a required input. One ciphertext means the proxy binding stays the single decrypt for vendor calls and the form renders from one table; the five GRA-6 `oauth_*` columns other than `oauth_refresh_state` are left unwritten and documented, awaiting a drop migration. (Field names are camelCase like the sibling scheme's, not the snake_case in the ticket brief.)

**Refresh, single-flight** — in the plugin's `derive`: the stored token is sent while good; within the skew of `expiresAt` or on a vendor 401 the refresh token buys a fresh one at the token URL, once per connection under concurrent calls (`runtime.once`, `single-flight.ts`), and the rotated record goes back to the host through a new `ProxyDeps.storeCredential` seam (`apps/server/src/connections.ts` binds it to `storeRefreshedCredential`). A refresh the endpoint refuses is not a refusal: the stored token goes out stale, **the vendor's own 401 reaches the tool untouched**, and `ProxyDeps.credentialRefreshFailed` marks the connection for re-consent (the console shows Reconnect). No token at all is a new outcome, `consent_required` (409). `ProxyEvent.oauth` is `refreshed | refresh_failed | null`. The scheme errors moved to `scheme-errors.ts` and the token-endpoint conversation to `oauth.ts`, shared by both OAuth plugins and the server's code exchange.

**The consent** — `@graft/core`: `startOAuthConsent` (PKCE S256 verifier written to `oauth_refresh_state.pkce`; authorize URL with the challenge, the redirect URI and a state HMAC-SHA256'd under `GRAFT_HANDOFF_SECRET` over `{connectionId, personId, pendingActionId|null, expiresAt (10 min), nonce}`; Google hosts get `access_type=offline&prompt=consent`), `completeOAuthConsent`, `storeRefreshedCredential`, `markOAuthConsentRequired`, `isConnectionUsable`. `ConnectionOutput` gains `oauth: { status: awaiting_consent | connected | consent_required, consentedAt, expiresAt, refreshedAt, consentRequired } | null` and never the verifier.

**Routes** (`apps/server`):
- `GET /api/oauth/redirect-uri` → `{ redirectUri }` = `GRAFT_AUTH_URL` + `/api/oauth/callback`, one function (`oauthRedirectUri`) the form and the callback's mount both read.
- `GET /api/oauth/callback?code&state` (no session; also `?error=access_denied`) → verifies the state, reads the verifier, **decrypts the client secret** (the second decrypt in this app, beside the proxy binding — `oauth.ts` says why), exchanges through the proxy's guarded fetch, stores the tokens, answers the ask `{ connectionId }`, renders a page that `postMessage`s the opener and posts on a same-origin `BroadcastChannel`.
- `POST /api/connections` with `credential` → `201 { connection, authorizeUrl }` for the scheme; the two GRA-28 submits do the same and leave the ask **open** for the callback to answer, so `request_connection` says connected only once the vendor can be called.
- `POST /api/connections/:id/oauth/authorize-url { pendingActionId? }` → `{ authorizeUrl, expiresAt, connection }` — Connect and Reconnect.

**MCP** — `request_connection` accepts the OAuth shape without `clientId`, reads a pending consent as not yet connected, and its awaiting answer carries `redirectUri` plus the three-sentence guidance; `McpDeps.oauthRedirectUri` (optional). The tool description and `describeSchemes()` say so.

**Console** — the form renders the client id from the table, the client secret as the one secret, the redirect URI fetched from the server beside them, and the Google Testing-mode notice for Google hosts only. Connect stores the client and opens the authorize URL in a popup; `useOAuthConsent` waits, then refreshes what changed. The card shows *awaiting consent* / *needs re-consent* with Connect / Reconnect; the credential ask on an OAuth connection is a reconnect, asking for the secret only after a revoke.

**Skill** — `skills/hermes-graft/connecting-with-oauth.md` (where to create the client, what to name it, which redirect URI to paste; Google as the worked example) and a paragraph in the authoring skill's connection section. GRA-31's `SKILL.md` is not on this branch, so the one-line pointer to the file is left to the merge.

## A finding worth reading

Google's consent pages send `Cross-Origin-Opener-Policy: same-origin` (checked against `accounts.google.com` by hand). That swaps the popup's browsing context group: `window.opener` is null on the callback page, so `postMessage` never reaches the console for Google, and the opener's handle reports the popup *closed* while the consent is still running. The console therefore treats the **poll of the connection** as the signal that always works, listens on the channel and the opener as bonuses, offers **Stop waiting**, and reads the popup's `closed` flag nowhere (`apps/web/src/lib/oauth-consent.ts`).
